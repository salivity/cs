How to Profile Memory Allocations in C

Measuring memory allocation is critical for optimizing .NET application performance and reducing garbage collection (GC) pauses. This article covers how to measure and track memory allocations in C# using modern allocation profilers, specifically the Visual Studio .NET Object Allocation tool, JetBrains dotMemory, and CLI-based diagnostic tools. You will learn how to configure a profiling session, interpret allocation call trees, pinpoint hot paths, and identify common memory churn issues like excessive boxing or object instantiation.

1. Profiling with Visual Studio .NET Object Allocation Tool

Visual Studio provides a built-in allocation tracker that records every heap allocation and attributes it to specific code paths without needing manual instrumentation.

  1. Open your project in Visual Studio and set the build configuration to Release mode for accurate compiler optimizations.
  2. Navigate to Debug > Performance Profiler... (or press Alt + F2).
  3. Under Available Tools, check .NET Object Allocation Tracking.
  4. Click Start to launch your application.
  5. Exercise the code path or user scenario you want to measure.
  6. Click Stop Collection to generate the diagnostic report.

2. Analyzing Allocation Data

Once collection stops, the profiler generates a summary dashboard containing several analytical views:

  • Allocation Summary: Displays a timeline of memory consumption alongside GC events (Gen 0, Gen 1, Gen 2). Look for steep upward slopes, which indicate rapid allocation rates that force frequent garbage collections.
  • Allocations Tab: Sorts memory consumption by object type. Look for high counts of common culprits like System.String, System.Byte[], or delegate closures.
  • Call Tree Tab: Identifies the exact execution path responsible for allocations. Expanding the tree reveals which methods allocate the most memory, helping you separate your application logic from framework overhead.
  • Functions Tab: Shows an inclusive vs. exclusive allocation breakdown per function. A high exclusive allocation count points directly to a method allocating objects within its own body rather than in downstream calls.

3. Profiling with JetBrains dotMemory

JetBrains dotMemory offers deep snapshot-based and timeline-based allocation tracking:

  1. Launch dotMemory and attach it to a running process, or start a new process under the Timeline profiling mode.
  2. In the Timeline view, monitor the Allocated in Heap metric in real-time.
  3. Select an interval where allocation spikes occur.
  4. Drill down using the Memory Traffic view. This view highlights transient objects that are allocated and immediately collected, which are prime targets for optimization.

4. Profiling in Production Using Command-Line Tools

For headless environments, containers, or production servers where GUI profilers are unavailable, use the official .NET CLI tools:

  1. Install the trace and dump tools:

    dotnet tool install -g dotnet-trace
dotnet tool install -g dotnet-gcdump

  2. Identify your process ID with dotnet-trace ps.

  3. Capture allocation statistics using the dotnet-trace GC allocation profile:

    dotnet-trace collect --process-id <PID> --profile gc-alloc

  4. Alternatively, capture a quick heap dump using:

    dotnet-gcdump collect -p <PID>

  5. Open the resulting .nettrace or .gcdump file in Visual Studio or PerfView to inspect object allocations and call stacks.

5. Acting on the Results

Once your profiler highlights the primary allocation sources, focus on standard .NET allocation reduction patterns:

  • Eliminate Boxing: Convert non-generic collections to generic collections, and replace value-type interface usage with generic type constraints.
  • Reuse Buffers: Implement ArrayPool<T>.Shared or MemoryPool<T> for temporary, large-byte arrays.
  • Zero-Allocation Slicing: Replace string manipulation methods like Substring with ReadOnlySpan<char>.
  • Avoid Closures: Ensure lambda expressions do not capture outer variables unnecessarily, which allocates closure classes on the heap.
